# Расширение редактора: контейнеры и печи

Анализ для Item Content 1.2.0, Minecraft 1.20.1 / Fabric. Дата: 12 ноября 2026 года.

Это предложение следующего этапа разработки. Описанные ниже контейнеры и печи в текущей версии не реализованы.

## Что есть сейчас

Item Content создаёт обычные блоки. Для них настраиваются внешний вид, твёрдость, взрывоустойчивость,
свет, звук и условия добычи. Варианты `decorative_chest` и `decorative_furnace` меняют форму
или оформление блока. Ни хранения предметов, ни плавки они не добавляют.

Это подтверждается реализацией:

- `src/main/java/dev/itemcontent/block/ContentBlock.java` наследует `Block` и описывает установку,
  поворот, форму и выпадение самого блока. Объекта хранения состояния блока, инвентаря и открытия окна нет.
- `src/main/java/dev/itemcontent/item/BuiltinFactory.java` создаёт один и тот же класс `ContentBlock`
  для обычного блока и обоих декоративных вариантов.
- `common/src/main/java/dev/itemcontent/definition/BuiltinTypes.java` предлагает им только общие свойства блока.
- `src/main/java/dev/itemcontent/api/ContentFactory.java` возвращает `Item` и необязательный `Block`.
  API не описывает общий этап регистрации типов объектов состояния блока, окон и клиентских обработчиков.
  Расширение может заниматься этим самостоятельно, но единого управляемого протокола пока нет.
- Формы редактора описывают отдельные простые свойства. Редактора слотов, вложенных правил и рецептов печи нет.

Поэтому представлять эти возможности как создание рабочих сундуков и печей неверно.

## Предлагаемый вариант

Сохранить один репозиторий Item Content и существующее отдельное приложение редактора.
Добавить в игровой мод несколько готовых видов поведения. Пользователь выбирает поведение
и заполняет понятные настройки; повторно писать механику для каждого бронзового сундука не требуется.

| Выбор пользователя | Что делает блок | Что настраивается |
| --- | --- | --- |
| Обычный блок | Ставится, ломается, имеет заданный внешний вид | Текстуры, форма, прочность, добыча |
| Контейнер | Открывает инвентарь и сохраняет содержимое | Название окна, 1–6 рядов по 9 слотов, доступ воронок, внешний вид |
| Печь | Принимает сырьё и топливо, выполняет рецепты, выдаёт результат | Набор рецептов, оформление выключенного и работающего блока |
| Поведение расширения | Выполняет механику установленного поставщика | Только свойства, которые поставщик явно открыл редактору |

Для первого выпуска контейнеров достаточно самостоятельного блока на 9–54 слота.
Автоматическое объединение двух сундуков, анимация крышки и нестандартные размеры окон — отдельные возможности,
которые должны иметь собственные проверки. Нельзя обещать их вместе с обычным инвентарём.

## Что использовать из Minecraft

### Контейнер

Стандартный `GenericContainerScreenHandler` уже имеет варианты окон от 9×1 до 9×6.
Его следует использовать для обычного контейнера без ограничений содержимого.
Содержимое хранится в объекте состояния каждого установленного блока (`BlockEntity`),
а не в общем описании его типа. Два одинаковых сундука должны иметь независимые инвентари.

Для изменяемого числа рядов разумнее небольшой общий контейнер на основе стандартных интерфейсов Minecraft,
чем копирование всего ванильного сундука. У ванильного `ChestBlockEntity` инвентарь на 27 слотов
и окно 9×3; простая смена текстуры не превращает его в контейнер произвольной вместимости.
Сохранение стаков должно использовать стандартную сериализацию Minecraft, сохраняя в том числе NBT других модов.

Если появятся ограничения по предметам, понадобится собственный обработчик слотов с тем же внешним видом:
готовое общее окно само по себе не обеспечивает произвольные фильтры. Правила вставки должны действовать
для клика, Shift-клика, перетаскивания, воронок и поддерживаемых интерфейсов автоматизации.

Источники: [окна контейнера](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/screen/GenericContainerScreenHandler.html),
[ванильный сундук](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/block/entity/ChestBlockEntity.html),
[слоты](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/screen/slot/Slot.html).
Размер инвентаря сундука также проверен по байткоду локальной сборки Minecraft 1.20.1.

### Печь

Для стандартной плавки использовать `AbstractFurnaceBlockEntity`, рецепты Minecraft и существующую
систему топлива. Она уже предусматривает вход, топливо, выход, прогресс и взаимодействие по сторонам.
Свой блок и свой зарегистрированный тип `BlockEntity` всё равно нужны: ванильный `FurnaceBlock`
создаёт `FurnaceBlockEntity`, выбирает обработчик обновлений для `BlockEntityType.FURNACE`
и при открытии проверяет конкретный класс. Наследовать блок без адаптации этих мест недостаточно.
Это проверено по байткоду используемой сборки 1.20.1.

Предлагаются два явно разных режима настройки рецептов:

1. Все обычные рецепты плавки Minecraft — поведение привычной печи.
2. Только выбранные рецепты — отдельный набор для конкретного типа печи.

Во втором режиме нельзя просто выгрузить новые рецепты как обычные `minecraft:smelting`:
они станут доступны обычным печам, а ограничение нашего блока не появится.
Нужен отдельный тип рецепта на основе стандартного cooking-рецепта и выборка по набору конкретного блока.
Подключение такого набора к ванильному циклу плавки требует небольшого проверенного адаптера.
Обычную плавку следует завершить и проверить до добавления многокомпонентных станков.

Базовый режим должен сохранять стандартную схему: одна единица сырья → одна единица результата.
В байткоде 1.20.1 видно, что при непустом выходном слоте ванильная плавка прибавляет именно один предмет.
Поэтому для выдачи нескольких предметов, результатов с разным NBT или числовыми параметрами
недостаточно добавить поле в JSON: нужен отдельный адаптер завершения операции и проверки совместимости стаков.
Это следующий уровень производственного поведения, а не обещание обычной печи.

Длительность и опыт можно задавать на уровне рецепта. Индивидуальный множитель скорости блока
или расхода топлива потребует дополнительной работы: часть состояния ванильной печи непублична.
Нельзя выдавать эти настройки за уже доступные простые переключатели.
Также строгий запрет любого неподходящего сырья требует своего правила приёма входного слота;
одно наследование ванильной печи не гарантирует нужную политику.

Источник: [AbstractFurnaceBlockEntity для 1.20.1](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/block/entity/AbstractFurnaceBlockEntity.html),
[блок печи](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/block/FurnaceBlock.html).

## Как должен выглядеть редактор

Создание контейнера:

1. Нажать **Создать → Блок**, ввести название «Бронзовый ящик».
2. Выбрать **Поведение → Контейнер**. Откроются только настройки контейнера.
3. Выбрать **Рядов: 6**. На предпросмотре появятся 54 слота и название будущего окна.
4. Выбрать текстуры и разрешить или запретить работу воронок.
5. Нажать **Проверить**, затем **Подготовить для игры**.

Создание печи:

1. Создать блок «Бронзовая печь» и выбрать **Поведение → Печь**.
2. Выбрать **Все рецепты плавки** либо **Свой набор рецептов**.
3. Для своего набора заполнить таблицу: **Сырьё | Результат | Время | Опыт**.
   Сырьё и результат выбираются из каталога с картинками; теги материалов — отдельным режимом выбора.
   В базовом режиме расходуется одна единица входа и выдаётся одна единица результата; произвольные количества и несколько входов
   относятся к следующему типу станка и не должны притворяться стандартной печью.
4. Назначить текстуры передней стороны в покое и при работе. Проверить предпросмотр.
5. Подготовить файлы и открыть инструкцию установки из редактора.

Название, внешний вид, поведение и рецепты должны быть отдельными понятными разделами выбранного блока.
Не показывать поля печи у обычного блока. Не требовать от пользователя имён Java-классов или ручного JSON.
Ошибки показывать рядом с конкретным полем и сохранять введённые данные.

Для этого текущих плоских `PropertyDefinition` недостаточно. Нужны типизированные описания настроек
контейнера/печи и элементы интерфейса для таблиц рецептов, выбора ресурсов и зависимых настроек.
Простые поля существующего API следует сохранить; сложные разделы добавлять совместимым расширением.

## Регистрация и API

Предлагаемая последовательность запуска игрового мода:

1. Загрузить и проверить определения, собрать перечень создаваемых блоков по поведению.
2. Создать и зарегистрировать блоки и предметы.
3. Зарегистрировать типы `BlockEntity` со всеми обслуживаемыми блоками до заморозки реестров.
4. Подключить обработчики окон и поддерживаемую автоматизацию.
5. На клиенте отдельно зарегистрировать необходимые окна и рендереры.

Один общий тип состояния на семейство поведения допустим, если фабрика получает настройки
из определения блока в переданном `BlockState`. Список поддерживаемых блоков фиксируется при регистрации.
Ссылка на тип состояния должна разрешаться после его регистрации, до первого создания объекта в мире.
Собственные окна нужны только там, где стандартного обработчика недостаточно.

Существующий `ContentFactory` и его конструкторы необходимо сохранить. Новый протокол регистрации
добавить отдельными совместимыми интерфейсами или default-методами, без обязанности переписывать простые расширения.
Клиентские классы не должны загружаться выделенным сервером.

## Сторонние моды и Item Parameters

Базовые контейнеры и печи работают самостоятельно. Установка Item Parameters для них не требуется.
Стандартные предметы других модов можно хранить без изменения их классов и NBT.
Для сторонних транспортных систем нужно проверить стандартный инвентарный интерфейс и Fabric Transfer API;
наличие собственного API у конкретного мода может потребовать отдельного моста совместимости.

Особые механики — энергия, жидкости, боеприпасы, магия — предоставляет установленное расширение.
Редактор показывает его описание и разрешённые настройки. Каталог не может восстановить произвольную механику
по Java-классу чужого предмета. Для новых текстур, моделей и сложных анимаций поставщик должен описать
ресурсы и при необходимости зарегистрировать рендерер. Нынешний список шаблонов моделей тоже потребуется расширить.

Для будущего производственного блока с числовыми формулами отдельный необязательный адаптер использует Item Parameters.
Его контракт: первоначальный расчёт или перенастройка → сохранение подтверждённых входов и выхода;
при производстве — проверка входов механизмом → использование сохранённого результата → создание выхода.
Новый вычислитель в Item Content не нужен. Конкретный вызов адаптера надо согласовать с реальным API
Item Parameters перед реализацией; данный анализ не является проверкой готовой интеграции.

## Сохранения, скорость и ограничения

- Описания блоков общие и неизменяемые во время работы. Стаки и прогресс принадлежат экземплярам в мире.
- Обычный контейнер не нуждается в серверном обработчике каждого тика. Анимация, если появится,
  обновляется отдельно на клиенте. Печь использует стандартный цикл обновлений загруженных блоков;
  отсутствие повторного вычисления формул не отменяет отсчёт времени производства.
- Рецепты загружаются при старте/перезагрузке данных. Не читать JSON и не обходить весь каталог на каждом тике.
  Последний подходящий рецепт можно запоминать с проверкой после изменения входа и перезагрузки рецептов.
- Состояние записывается в NBT; синхронизация окна использует механизмы Minecraft.
  Сервер проверяет доступ к блоку, действия со слотами и завершение операции.
- Старые декоративные типы сохраняют прежнюю семантику. Рабочим типам дать новые ID поведения.
  Добавление новых типов реестра требует перезапуска клиента и сервера.
- При уменьшении вместимости нельзя молча обрезать сохранённый инвентарь. Нужен запрет такого изменения
  для существующих сохранений либо отдельная миграция с сохранением излишков. Политика должна быть выбрана до выпуска.
- Количество определений и количество установленных блоков — разные нагрузки. До замеров нельзя обещать
  конкретное число работающих печей или объём памяти. Проверять отдельно простой, обработку и открытые окна.

## Этапы и критерии готовности

1. **Контейнер:** хранение, обычное окно, установка/добыча, сохранение, воронки. Проверить два независимых
   экземпляра, все размеры, полные стаки и стаки с NBT, перезапуск, выгрузку чанка, двух игроков одновременно,
   Shift-клик, перетаскивание и разрушение без потери или удвоения содержимого.
2. **Печь:** обычные рецепты, топливо, прогресс, выход, работающий внешний вид. Проверить отсутствие топлива,
   заполненный выход, несовместимые стаки, остатки топлива вроде ведра, остановку и возобновление,
   опыт, автоматизацию и перезапуск посреди обработки. Затем проверить изоляцию собственных наборов рецептов,
   изменение входа и перезагрузку рецептов. Если заявлен строгий фильтр — проверить все способы вставки.
3. **Редактор:** весь путь от пустого документа до игры без ручного JSON; сохранение/открытие всех настроек,
   ошибки без потери ввода, предпросмотр слотов, разные масштабы интерфейса, читаемые подписи и готовый экспорт.
4. **Расширения:** тестовый поставщик с собственным поведением, установка без поставщика с понятной ошибкой,
   отдельный запуск выделенного сервера, проверка старого API и прежних документов.
5. **Производительность:** одинаковый мир и условия для ванильной и новой печи; отдельно измерить серверное
   время тика, память, сохранение и сеть на нескольких размерах нагрузки. Указать оборудование и условия,
   а не публиковать скорость только одного пустого блока.

До реализации и прохождения этих проверок корректное описание продукта — редактор предметов и обычных блоков.
Рекомендуемый следующий этап — контейнер с полноценным хранением; затем печь на готовой механике Minecraft.
